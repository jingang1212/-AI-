# 代码审查记录（自审）

> 审查范围：`app/`、`scripts/`、`evaluation/` 与数据层设计。
> 审查方式：逐模块读代码 + 真实运行（不是纸面审查），每条都尽量给出复现路径。
> 记录格式：现象 → 影响 → 根因 → 处理。

## 一、严重（已修复，都会导致功能不可用或结论错误）

### 1. 时区不一致：现场有数据，平台却显示「无数据」
- 现象：seed 用 `datetime.now(timezone.utc)` 写监测数据，而查询窗口按本地时间算，
  两者差 8 小时。
- 影响：用户问「最近 24 小时情况」，实际查的是 8 小时前的窗口；
  现场明明有数据，助手回答「没有数据」，运维白跑一趟。
  更隐蔽的是日/小时均值会跨错时段，直接影响超标判定。
- 根因：全项目没有统一的「业务时间」口径，各处自己 `datetime.now()`。
- 处理：新增 `app/timeutil.py` 统一时区（默认 `Asia/Shanghai`，可由 `TZ_NAME` 覆盖），
  seed、设备工具、报告工具全部改用它；老数据带 `Z` 后缀也能兼容解析。

### 2. 空语料导致 BM25 崩溃：`ZeroDivisionError`
- 现象：知识库还没导入任何文档时查询，`rank_bm25` 的 `BM25L([])` 内部
  `avgdl = num_doc / corpus_size` 除零。
- 影响：用户看到的是一个看不懂的除零异常，而不是「知识库为空」。
- 根因：`build_index` 没有处理空列表（`rank_bm25` 库本身不健壮）。
- 处理：`build_index([]) -> None`，`rank_with_index(index=None) -> []`，
  空语料下检索正常返回空结果。

### 3. 向量库原生崩溃（chromadb）
- 现象：`scripts/ingest.py` 无任何报错、退出码 1。
  用 `python -X faulthandler scripts/ingest.py` 才看到
  `Windows fatal exception: access violation`，崩在 `chromadb/api/rust.py` 的
  `_upsert` / `_delete`。
- 影响：知识库完全无法构建，且 Python 层抓不到异常（不是 try/except 能救的）。
- 根因：chromadb 的 Rust 引擎在本机环境不兼容。
- 处理：向量库抽象成 `add_chunks / search / get_all_chunks` 三个函数，
  本地用 numpy 实现，生产切 Milvus（文件末尾附完整写法），业务代码零改动。

### 4. 提示词与工具不一致：主管会调用「不存在的员工」
- 现象：系统提示词里写死了三个员工，但 `leader` 角色实际只绑定两个。
- 影响：模型反复尝试调用不可见的员工 → 报错 → 反复道歉，答非所问。
- 根因：提示词静态拼接，没有按角色可用性过滤。
- 处理：`build_system_prompt` 改为按 `build_staff_tools(role)` 动态生成员工清单。

### 5. 熔断后返回空回答
- 现象：主管撞到 `MAX_ROUNDS` 上限时，最后一条 AIMessage 只有 tool_calls、没有正文。
- 影响：前端拿到空字符串，表现为「一直转圈」，用户以为系统坏了。
- 根因：只取最后一条 AIMessage，没考虑它可能没有可读内容。
- 处理：从后往前找「不带工具调用的 AI 消息」；仍为空时给一句可理解的提示。

### 6. rerank 失败被静默吞掉
- 现象：`except Exception: pass`，云端 rerank 不可用时没有任何提示。
- 影响：检索质量下降但无人知晓，用户以为「系统就这个水平」。
- 处理：保留降级（rerank 是精排环节，不该拖垮问答），但打印一次带人话的失败原因。

## 二、中等（已修复，影响性能、安全或数据正确性）

### 7. BM25 索引每次查询都重建
- 影响：语料几十万字时每次问答多花 1~2 秒纯 CPU 时间，而且是串行开销。
- 处理：`hybrid.build_index` / `rank_with_index` 拆分，`rag` 按语料版本号缓存索引；
  `vectorstore` 在写入/删除后自增版本号自动失效。

### 8. 标量过滤（kb_id）没实现
- 影响：技术方案里写了「Milvus 按 kb_id/tenant_id 过滤」，代码却没有写入该字段，
  等于安全设计没落地；事后补要全量重灌向量。
- 处理：入库写入 `kb_id`，检索支持 `kb_id` 过滤（向量与 BM25 两条通道都过滤，
  否则会出现「向量过滤了、关键词没过滤」的越权泄漏）。

### 9. 告警只查设备维度，漏掉站点级告警
- 影响：站点级告警（如「站点数据中断」）查不出来，助手回答「无告警」，与平台页面不一致。
- 处理：设备维度 + 站点维度 `UNION ALL` 一起查，并在输出里区分 `设备/站点`。

### 10. 报告工具把服务器绝对路径返回给用户
- 影响：泄漏服务端目录结构，对用户也没有意义。
- 处理：只返回文件名，完整路径仅记录在执行轨迹里（供前端做下载入口）。

## 四、账户与额度问题的处理策略（明确决策）

云端返回的 `Arrearage`（欠费/额度用尽）属于**外部状态问题，不是代码问题**。

- **不做本地兜底**（曾实现过哈希向量降级，已回退）：降级写入的向量与云端向量空间
  不兼容，一旦混用会污染知识库，排查成本远高于「停机充值」；
- **只给明确提示**：`app/embeddings.py` 把 `Arrearage / overdue-payment / InvalidApiKey`
  翻译成中文提示（到哪一步、做什么），其余错误原样抛出；
- rerank 失败降级到 RRF，但提示一次；
- 恢复后必须重新执行 `scripts/ingest.py`（向量模型不可用时没有写入任何数据，
  所以不存在脏数据，这一点在设计上是可恢复的）。

## 五、D4 新增发现（流式双协议开发期间）

### 17. DashScope 流式 tool_calls 分片：手写合并必踩的坑

- 现象一：主管每轮都出现 `派活 → （空名字）` 的幽灵调度，员工全部执行失败，
  主管 6 轮循环后只能道歉收尾。
- 现象二：工具参数（task 文本）被截断成两个字，员工拿到的任务不完整。
- 根因：DashScope 把工具参数按 **JSON 字符串分片** 下发（`{"task": "用户`、
  `（安装/运维`、`工程师）反馈：...`），LangChain 归一化后部分分片 id 为空、
  部分分片被提前 `json.loads` 成 dict；手写合并时「空 id → 新调用」「dict → 按 key 覆盖」，
  一个产生幽灵调用，一个覆盖丢了文本。
- 处理：改用 LangChain 官方的 `AIMessageChunk + AIMessageChunk` 加法合并
  （`__add__` 内部按 index 聚合分片并统一解析），并用探针脚本先验证再上线。

### 18. `AIMessage(tool_calls=None)` 直接抛 pydantic 校验错

- 现象：主管流式回答已全部推给前端，紧接着报
  `1 validation error for AIMessage: tool_calls Input should be a valid list`，
  触发兜底重试，导致**同一段回答推了两遍**。
- 根因：pydantic 2 下 `tool_calls` 字段不接受显式 None。
- 处理：None 时不传该字段，用默认值。

### 19. uvicorn 进程里的 print 同样踩 GBK

- 现象：服务启动即崩（lifespan 里 print ✅）。
- 处理：`app/api/main.py` 入口统一调用 `setup_console()`。教训是
  「修复要放在最外层入口」——脚本入口修了不代表服务入口也修了。

### 20. 服务进程没有出网权限 → 全部请求报 Connection error

- 现象：测试客户端一切正常，服务端模型调用全部 `Connection error.`，
  排查半天才定位到是「服务进程启动在无网络的环境里」。
- 教训（通用）：分布式排查第一刀永远是「出问题的是哪一层」，
  先直接 curl 模型网关，再怀疑代码。

### 21. 角色收敛用 fail-closed

- 客户端可传 role（演示便利），未知角色一律落到权限最小的 `service`，
  而不是默认给高权限 `ops`。攻击者乱填角色只会拿更少能力。

## 六、D5 新增发现（人工确认 + 图表）

### 22. langgraph 1.2 的 `ainvoke` 不再抛 GraphInterrupt

- 现象：单测里 `interrupt()` 既不抛异常也不挂起，第一次调用「静默完成」，
  第二次调用才把 resume 值返回给节点。
- 根因：langgraph 1.2 改变了语义——`graph.ainvoke` 中断时**返回的 state 里带
  `__interrupt__` 列表**（`[Interrupt(value=...)]`），而不是抛异常；
  老教程里的 `except GraphInterrupt` 写法只适用于旧版或 `stream()` 路径。
- 处理：`arun` 同时兼容两种形态（state 检查 + 异常兜底），
  恢复时 `Command(resume=决定)` 会从节点开头重跑，节点逻辑必须幂等。

### 23. 员工工具清单漏注册 + 员工倾向「叙述代替调用」

- 现象一：员工报告「工具箱里没有 update_device_config」——确实没注册
  （只加了提示词没加 tools 列表）。提示词和工具清单必须同改，最好加一个
  「每个 STAFF_SPECS 里声明的工具名都能在注册表找到」的启动自检。
- 现象二：模型反复用大段文字描述「已发起提案、等你批准」，实际从未调用工具，
  数据库没有任何写入——**叙述 ≠ 执行**，排查时永远以「数据库/日志有没有变化」
  为准，不要信模型的自我陈述。
- 缓解：员工第一步 `tool_choice="required"` 强制动手；但模型仍可能选择
  查状态而不是写工具，这属于模型行为，需要评测集 + 提示词迭代来收敛。

### 24. 静态演示数据会「过期」

- 现象：seed 写入的是固定时间的心跳，几十分钟后再跑测试，所有设备都变成
  「离线 30 分钟」，模型因此拒绝远程改参（它是对的）。
- 处理：测试脚本在断言前刷新心跳时间；真实系统里设备每分钟上报，
  不存在这个问题，但「演示数据要带时间推进逻辑」值得记住。

## 七、前端聊天页开发期间

### 25. FastAPI 把 `mount("/")` 写在路由之前会吞掉 /healthz

- 现象：加完前端静态目录后，`/healthz` 全部 404，而首页正常——用户会看到
  页面能打开、状态灯却显示「后端不可达」。
- 根因：FastAPI/Starlette **按代码执行顺序注册路由**，`@app.get("/healthz")`
  装饰器写在 `app.mount("/", StaticFiles)` 之后，Mount 先注册、先匹配，
  把所有路径都抢走了。
- 处理：把 healthz 移到所有 mount 之前。教训：**挂载 "/" 必须放在最后**，
  且写完要用真实浏览器打开首页看状态灯，而不是只 curl 首页。

## 八、Redis 集成踩坑（含本机 Redis 升级）

### 26. redis-py 5 默认 RESP3 握手，Redis 5 直接报 unknown command HELLO

- 现象：本机 Redis 5.0.14 上所有连接失败 `unknown command HELLO`。
- 根因：redis-py 5.x 建连时用 `HELLO 3` 协商 RESP3 协议，Redis < 6 不支持。
- 处理：客户端统一 `protocol=2` 显式降级（checkpointer 探测、pending 客户端都带）。
  顺带升级：本机 Redis 5.0.14 → **Memurai 7.2.5**（winget 安装，注册为系统服务）。

### 27. langgraph 的 Redis checkpointer 依赖 RedisJSON 模块

- 现象：Redis 能 ping 通，但第一次问答就抛 `unknown command JSON.SET`。
- 根因：RedisSaver 底层用 redisvl 建 JSON 索引，需要 RedisJSON（原版 Redis、
  Memurai 都不带；只有 Redis Stack 镜像 `redis/redis-stack-server` 内置）。
- 处理：启动时探测 `JSON.SET`，不支持就**降级内存 checkpointer** 并打印
  一条可执行的提示（含 redis-stack 的 docker 命令），而不是运行时才崩。

### 28. 确认登记表的 key 类型冲突：SET 标记 + BRPOP 同一个 key = WRONGTYPE

- 现象：wait_decision 先 `SET key "1"` 再 `BRPOP key`，Redis 报 WRONGTYPE。
- 根因：SET 存字符串，BRPOP 要求列表，两者不能共用 key。
- 处理：拆成 `:waiting`（string 标记）+ `:list`（list 决定）两个 key；
  投递方靠 waiting 标记判断「有没有人在等」，等待方超时清两个 key。
  这是真实跑出来的协议 bug，`scripts/test_redis.py` 已覆盖。

## 九、生态化整改（Milvus/jieba 真接入，清理死代码）

### 29. Milvus Lite 在 Windows 可用，但 pip extra 装不上

- 现象：`pip install "pymilvus[milvus_lite]"` 退出码 0，但 `import milvus_lite`
  依然 ModuleNotFoundError；必须**单独** `pip install milvus-lite==3.2.2` 才生效。
- 结论：依赖声明里两个包分开写（pyproject 已如此）。

### 30. MilvusClient 快速建表的两个 schema 坑

- 坑一：`create_collection(dimension=..., primary_field_name="chunk_id", auto_id=False)`
  会把主键推断成 INT64，传字符串主键报 `DataNotMatchException`；
  必须显式 `create_schema` + `FieldSchema(VARCHAR, is_primary=True)`；
- 坑二：`enable_dynamic_field=False` 时 insert 少任何一个声明字段都会报
  `Insert missed an field`——加字段后旧代码全部要跟着补。

### 31. 自定义主键下检索结果的取法

- `search` 返回的 hit 用 `h["id"]` 会 KeyError（只有默认主键才有）；
  自定义主键要用 `h["entity"]["chunk_id"]`。

### 32. upsert 只覆盖同主键，「文档变短」必须先删后写

- 单测 `test_milvus.py` 真实再现：docA 从 3 块改版成 2 块后重新 upsert，
  旧的第 2 块残留（脏尾巴），`kb_id` 过滤会多命中一条。
- 正确流程 = `rag.index_document` 现在的实现：先 `delete_document` 再写。

### 33. 冗余项整改清单（本轮已执行）

- `jieba`：由「声明但未用」改为真正接入（索引 lcut / 查询 cut_for_search），
  缺失时保留字符级切分兜底；
- 删除：`hybrid.bm25_rank`（无调用方）、`langchain` / `langchain-community` /
  `langchain-chroma` 三个未使用依赖；
- `vectorstore.reset()`：接入 `scripts/ingest.py --reset`，变成可用功能；
- 向量库：手写 numpy 实现降级为「应急兜底」，默认走 Milvus（Lite/服务端同套代码）。

## 十、充值后的全链路复测

### 34. Milvus 集合要先 load 才能检索

- 现象：入库成功后评测第一题就报 `code=101, collection is in state 'released'`。
- 根因：Milvus 服务端语义里集合要 `load_collection` 进内存才能 search/query，
  新建集合默认 released（嵌入式 Lite 同样复现）。
- 处理：建表和已存在分支都调用 `load_collection`（幂等）。

### 35. 检索 output_fields 漏主键 → 所有命中的 key 塌成空串

- 现象：混合检索返回正常但每条 `score=0.0`、排序变成纯 BM25 顺序。
- 根因：`search(output_fields=...)` 没包含自定义主键 `chunk_id`，
  命中的 entity 里没有 key，RAG 层合并时 vec_map 的 key 全为空字符串。
- 处理：output_fields 显式带上 `chunk_id`。教训：**自定义主键不是自动返回的**。

### 36. 法规文档的罚则条款被片段截断

- 现象：问「篡改数据怎么处罚」，知识员工连查 10 次仍说「拿不到可引用条款原文」，
  主管反复派单 5 轮，token 消耗暴涨。
- 根因：分块 800 字/块，而工具把片段截到 400 字再给模型，
  罚则（十万元以上一百万元以下罚款）恰好落在被截掉的后半段。
- 处理：`SNIPPET_CHARS` 400 → 900（覆盖一整块 + 重叠余量）。
  遗留注意：法规类长文档建议分块更细（按条款），这是下一轮语料优化方向。

### 37. 正式评测数字（2026-10-15，充值后全链路实测）

59 条评测集 × 14 篇语料（26 chunk），Milvus(HNSW/COSINE) + BM25(jieba) + RRF(k=60)
+ qwen3.7-text-rerank：

| 指标 | 结果 |
|---|---|
| recall@3 | 98.31%（58/59） |
| recall@5 | 100%（59/59） |
| recall@8 | 100%（59/59） |

注：评测跑一次约 8 分钟（59×3=177 次查询，每次含 embedding + rerank 两次云端调用），
改提示词/分块参数后请把 `evaluation/evaluate.py` 作为回归必跑项。

## 十一、认证与租户隔离落地（SQLite 演示版）

### 38. Milvus Lite 是单进程嵌入式：服务运行中无法入库

- 现象：服务跑着时执行 ingest，报 `DataDirLockedError`（另一个进程持有文件锁），
  随后**静默降级到 numpy 把向量写进了另一个文件**——两套数据分家，
  healthz 显示 milvus 但搜出来是空的，非常隐蔽。
- 根因：Milvus Lite 单进程独占数据文件；这是嵌入式模式的固有限制，
  不是 bug。生产用 Milvus 服务端没有这个问题。
- 处理：降级提示里识别 `lock` 字样，明确告诉「先停服务再入库」；
  本次已清理分家数据并重灌。教训：**嵌入式组件和长驻服务不能同时持有数据**。

### 39. AI 工具层的范围校验实测生效

- 场景：ops_01（只授权华能热电）问「CEMS-003 状态」（设备 3 属企业 3），
  员工调 `device_status` 被工具层拦下，返回「当前账号无权访问设备 3」，
  模型随后只能给出通用排查步骤、拿不到真实心跳数据——纵深防御按设计工作。
- 结论：工具层校验是 AI 场景最后一道闸（模型会自己编参数），必须有。

## 十三、回答截断 + 安装/运维同人整改（2026-10-15）

### 45. Web 端完整回答被 500 字截断

- 现象：最终回答被切成 500 字，长回答（排障步骤、报告说明等）说到一半戛然而止。

## 十四、写操作「只叙述、不执行」+ 中断被吞（2026-10-15）

### 47. 写工具的人工确认中断被层层 try/except 吞掉

- 现象：问「把 CEMS-003 波特率改成 9600」，前端收不到 interrupt 事件，也不写库，
  主管只回「提案已提交，待批准」的叙述，实际什么都没发生（含 6 轮未收敛的情况）。
- 根因：interrupt() 抛出 GraphInterrupt，但 run_staff 的工具调用处、graph.staff_node
  的 run_one 处都有 `except Exception` 兜底，把 GraphInterrupt 一并吞掉转成错误文本，
  图引擎永远收不到中断信号，确认链路走不到。
- 处理：在 staff.py 两处、graph.py 一处的 `except Exception` 之前显式加
  `except GraphInterrupt: raise`，让中断信号冒泡到图引擎；其余异常仍转文字回给模型。

### 48. 更正：写操作靠 function calling 就能走通，「模型没调用」是误判

- 复查实验：用 ops_staff 的系统提示词 + tool_choice="required" 直接问两个写请求，
  模型两次都正确返回 update_device_config 及其完整参数——function calling 本身是好的。
- 更正结论：此前「模型只叙述、不调用工具」（含 §23）是从「库里没变化」倒推的，
  不可靠；真实原因是 §47 的中断被 except Exception 吞掉——工具被调用了，
  但 interrupt 没冒泡，库自然没变化，表象与「没调用」完全一致。
- 处理：曾加「确定性写意图直调工具」作为兜底，复查后已回退该路径，
  保留「函数调用 + 中断冒泡」的原始架构；去掉兜底后实测写链路完整通过。

## 十五、去兜底化整改：坏兜底删除，好兜底保留（2026-10-15）

原则：**允许降级，但不允许「错得不可见」**。
- 降级后结果依然正确、且降级本身可见（打日志/可感知差异）→ 保留；
- 降级后结果悄悄变差变错、且无人知晓 → 删除，改为失败即报错。

删除（原本是有害的静默降级）：

- 向量库：删除 numpy 应急实现与「Milvus 初始化失败 → 降级 numpy」逻辑，
  Milvus 失败直接抛异常（锁文件等错误原样暴露）。
- Redis checkpointer：删除「缺 RedisJSON / 连不上 → 降级内存」逻辑，
  改为服务启动时校验（连通性 + JSON.SET），校验失败直接启动报错；
  `checkpointer_backend` 按配置返回 redis / memory。
- jieba：删除「缺失时退回单字+二元组切分」逻辑，直接 import jieba，
  缺依赖在导入期报错。
- 时区：删除「缺 tzdata 退回固定 +08:00」逻辑，改抛异常并提示 pip install tzdata。
- 文档解析：删除「UTF-8 失败退回 GBK(errors=ignore)」逻辑，改报错要求转 UTF-8。
- 导入脚本：ingest.py 从「跳过失败文件继续」改为「汇总失败并以退出码 1 结束」。

保留为「可见降级」：

- rerank：失败退回 RRF 顺序，但打印一次带人话的失败原因（排序增强器坏了
  宁可排序稍差，不拖垮问答；降级可见）。
- 模型调用：tool_choice="required" 失败退回 auto 重试一次；auto 再失败
  会把原始错误抛给上层，不会被吞掉。
- 图表：无中文字体时退回英文标签并提示一次（图仍正确可用），不阻断服务。
- 前端：dist 不存在时以纯 API 模式启动并打日志，需要页面时构建后重启。

说明：test_redis.py 断言相应更新；.env 的 REDIS_URL 已注释（本机 Redis 无
RedisJSON），如需会话持久化请换 Redis Stack 并重新配置。
