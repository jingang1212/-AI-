# 环保监测智能运维 AI 助手 —— 详细技术方案

> 目标：从零实现一个可运行、可演示、面试可深挖的 AI 助手后端。
> 技术栈：Python、FastAPI、LangChain、LangGraph、Milvus、BM25、RRF、rerank、WebSocket、SSE、MySQL、Redis。

---

## 1. 项目概述

**背景**：环保监测场景，企业污染源在线监测数据由设备采集，需要两类能力——
1. 知识库检索问答（法规、规范、设备手册、运维 SOP）；
2. 多智能体协作（运维排查、数据分析、报告生成）。

**用户**：运维人员（查设备、排障）、监管人员（查数据、看报告）。

**核心场景**：
- 「帮我查一下 D001 站点的二氧化硫最近 24 小时趋势，并生成分析报告」→ 主管 → 运维员工查数据 + 报告员工生成报告。
- 「设备离线了怎么办」→ 主管 → 知识员工检索 SOP + 运维员工查设备状态。

## 2. 总体架构

### 2.1 分层架构

```
┌──────────────────────────────────────────────────────────┐
│ 接入层   FastAPI                                          │
│   /ws/chat      WebSocket（双向：语音、卡片、打断）          │
│   /sse/chat     SSE（单向流式：Web 端聊天、报告进度）        │
│   /api/docs     REST（文档上传、设备/数据查询）              │
├──────────────────────────────────────────────────────────┤
│ 编排层   LangGraph StateGraph                              │
│   Supervisor（主管）→ 员工 Agent（运维/知识/报告）→ join     │
├──────────────────────────────────────────────────────────┤
│ 工具层   LangChain Tools（+ 可选 MCP）                      │
│   knowledge_search / device_status / query_data /          │
│   generate_report / load_skill / read·write·edit_table     │
├──────────────────────────────────────────────────────────┤
│ 检索层   RAG                                              │
│   解析 → 分块 → 向量化 → Milvus                             │
│   混合检索：向量 + BM25 → RRF(k=60) → rerank                │
├──────────────────────────────────────────────────────────┤
│ 数据层   MySQL(业务) · Redis(会话/缓存) · Milvus(向量)       │
└──────────────────────────────────────────────────────────┘
```

### 2.2 一次请求的完整时序（以「查 D001 站点 SO2 趋势并出报告」为例）

```
用户 → /ws/chat 发文本
  → Supervisor 理解意图：需要「查数据 + 出报告」
  → 并行调度两个员工：ops_staff(查数据)、report_staff(出报告)
  → ops_staff 调 query_data 工具 → MySQL 查监测数据
  → report_staff 调 generate_report 工具 → 生成 Markdown 报告
  → join 汇总 → Supervisor 整合 → 流式推回用户
```

## 4. RAG 模块详细设计

### 4.1 文档解析（loader.py）

```python
def parse(filename: str, content: bytes) -> str:
    if filename.endswith(".pdf"):
        from pypdf import PdfReader
        text = "\n\n".join((p.extract_text() or "") for p in PdfReader(BytesIO(content)).pages)
        if not text.strip():
            raise ValueError("扫描件，需要 OCR")
        return text.strip()
    if filename.endswith(".docx"):
        from docx import Document
        return "\n".join(p.text for p in Document(BytesIO(content)).paragraphs)
    return content.decode("utf-8")   # md / txt
```

**异常处理**：扫描件拦截、非 UTF-8 转 GBK、空文本报错——**宁可报错也不入库空块**。

### 4.2 分块（splitter.py，4 种策略）

| 策略 | 实现 | 参数 |
|---|---|---|
| 固定字符 | RecursiveCharacterTextSplitter(separators=["\n\n","\n"," ",""]) | chunk_size=800, overlap=100 |
| Markdown 标题 | MarkdownHeaderTextSplitter(headers_to_split_on=[#,##,###]) | 记录 headingPath |
| 段落 | 按 `\n\n` 聚合 | 超长再按固定切 |
| 递归语义 | 按句子边界(。！？)递归合并 | 按语义完整 |

```python
def chunk(text, strategy="fixed", size=800, overlap=100):
    if strategy == "fixed":
        return RecursiveCharacterTextSplitter(
            chunk_size=size, chunk_overlap=overlap,
            separators=["\n\n", "\n", "。", " ", ""]).split_text(text)
    ...
```

每个 chunk 的 metadata 记录 `chunk_index / start / end / heading_path / source`，用于引用定位。

- 批量：每批 10 条
- 维度校验：`len(vector) != 1024` 直接报错

### 4.5 混合检索（retrieve.py，核心）

```
输入 query
  ├─ 向量召回：embed(query) → Milvus.search(top20)
  ├─ BM25 召回：jieba 分词 → rank_bm25 打分 → top20
  ├─ RRF 融合：score = Σ 1/(60 + rank)
  └─ rerank 精排：对候选逐对打分 → top_n=5
```

```python
def tokenize(text):   # 中文单字+二元组，英文整词
    tokens = [w for w in re.findall(r"[a-zA-Z0-9_]+", text.lower())]
    cjk = re.findall(r"[\u4e00-\u9fff]", text)
    tokens += cjk
    tokens += ["".join(cjk[i:i+2]) for i in range(len(cjk)-1)]
    return tokens

def rrf(vector_keys, bm25_keys, k=60):
    scores = {}
    for keys in (vector_keys, bm25_keys):
        for rank, key in enumerate(dict.fromkeys(keys), start=1):
            scores[key] = scores.get(key, 0) + 1/(k+rank)
    return sorted(scores.items(), key=lambda kv: -kv[1])
```

```python
recall@k = 命中期望来源的条数 / 总条数
```

## 5. Agent 模块详细设计

### 5.1 LangGraph 图结构（agents/graph.py）

```python
class State(TypedDict):
    messages: Annotated[list, add]
    task_calls: list          # 主管分配的任务

g = StateGraph(State)
g.add_node("supervisor", supervisor)
g.add_node("ops_staff", ops_staff)
g.add_node("knowledge_staff", knowledge_staff)
g.add_node("report_staff", report_staff)
g.add_node("join", join)
g.add_edge(START, "supervisor")
g.add_conditional_edges("supervisor", route, {
    "ops_staff": "ops_staff", "knowledge_staff": "knowledge_staff",
    "report_staff": "report_staff", "join": "join"})
# 员工完成后都回到 supervisor 汇总，或进 join
g.compile(checkpointer=MemorySaver())
```

### 5.2 Supervisor（agents/supervisor.py）

```python
llm = ChatOpenAI(model="qwen-plus", base_url=..., temperature=0.3)
chain = prompt | llm.bind_tools([ops_staff_tool, knowledge_staff_tool, report_staff_tool],
```

### 5.5 循环控制与人工确认

- 员工工具循环：LLM 结构化输出 `{action: CONTINUE|FINISH}`，FINISH 或超迭代上限则提交任务；
- 人工确认：`select_the_company / select_the_station / select_the_device / draw_chart` 等工具挂 `interrupt`，用户确认后 `Command(resume=...)` 恢复。

---

**D5 落地说明**（实现与方案有两处差异，都是实测后改的）：

1. 员工工具循环从「结构化输出 CONTINUE/FINISH」改为**按 tool_calls 是否为空判断收敛**
   + 4 步熔断——结构化输出多一次模型调用，且小模型输出格式不稳；
2. 人工确认用 LangGraph `interrupt()`，注意 langgraph 1.2 的坑：
   `graph.ainvoke` **不抛 GraphInterrupt**，而是把 `__interrupt__` 放进返回的状态里，
   要用 `state["__interrupt__"][-1].value` 取 payload，再 `Command(resume=决定)` 恢复。
   恢复时会**从节点开头重跑**，所以写工具里「先读旧值再提议」的逻辑必须是幂等的。

写操作安全链（`app/tools/write.py` + `app/services/config_service.py`）：

    参数白名单（只允许波特率/上报地址/采样周期）→ 值域校验 →
    interrupt 挂起 → 前端 POST /api/chat/confirm 批准/拒绝 →
    参数化 SQL 写单表单行 → op_log 留痕（原值→新值/操作人/来源/时间）

验证方式：`scripts/test_confirm_unit.py`（确定性单测，不需要网络）覆盖
「批准 → 落库留痕」「拒绝 → 不写入」「白名单拦截」三条路径。

### 6.2 WebSocket 端点（api/ws_chat.py）

- 鉴权：连接时校验 token
- 消息类型：`text` / `record`(语音) / `abandon` / 中断回复
- 发送：独立 `sender` 协程 + `asyncio.Queue`，业务侧只往队列丢
- 断开：清理 checkpoint、取消协程

### 6.3 SSE 端点（api/sse_chat.py）

```python
@app.post("/sse/chat")
async def sse_chat(body):
    async def gen():
        async for evt in agent.run(body.message):
            yield f"data: {json.dumps(evt, ensure_ascii=False)}\n\n"
    return StreamingResponse(gen(), media_type="text/event-stream")
```

### 6.4 为什么并存

| 端 | 协议 | 原因 |
|---|---|---|
| Web 浏览器 | SSE | 原生 EventSource / fetch 流式，简单 |
| 微信小程序 | WebSocket | 小程序不支持 SSE/EventSource |
| 语音/卡片 | WebSocket | 需要双向 + 打断 |


关键实现点（面试可讲）：

- **流式 token**：主管用 `bound.astream`，token 增量通过 trace 的 `content.delta` 事件
  实时进队列；LangGraph 状态里存的仍是合并后的完整 AIMessage；
- **AIMessageChunk 加法合并**：手写过一次分片合并，被「空 id 幽灵调用 + 参数分片
  被提前解析成 dict 覆盖」坑了（详情见审查记录 §五），最终用 LangChain 官方的
  `chunk + chunk` 合并，探针验证参数完整还原；
- **降级提示**：知识库工具因欠费失败时，员工把错误转成文字交回主管，
  主管能继续用设备/数据工具回答（SSE/WS 实测均正常收敛）。

### 13.2 漏洞 / 风险（必须处理）

1. **rerank 是最大落地风险**：本地 bge-reranker 要 torch/GPU，很重；API 要额外服务。落地策略：D2 先做「向量 + BM25 + RRF」跑通并评测，rerank 做成可选插件，没有就跳过。**简历写 rerank 的前提是真接了一个。**

2. **Chroma 阶段没做权限过滤**：方案里 Milvus 有 tenant_id 过滤，但 Chroma 阶段没体现。切 Milvus 时要补标量过滤。落地：D1 就把 `tenant_id` 写进 chunk metadata，接口预留过滤参数，做到「先设计后实现」。

3. **BM25 全量扫描性能**：数据小没问题，数据大时全量打分慢。面试答法：换 ES，或维护增量 BM25 索引。

4. **多智能体排期偏乐观**：D3 一天做完 Supervisor + 3 员工 + 工具循环 + 人工确认不现实。落地：D3 先「1 个主管 + 1 个员工 + 1 个工具」跑通，再横向复制成 3 个员工。

5. **语音可砍**：ASR/TTS 依赖阿里云实时识别服务，demo 阶段可先不做，简历要写语音就必须真做。

6. **评测集要自己编 20~50 条**：方案没写从哪来。落地：按「问题 → 正确答案所在文档」手工编 30 条，覆盖排放标准、运维 SOP、安装手册、法规四类。

7. **监测数据缺 seed**：D3 起员工 Agent 要查设备状态/监测数据，MySQL 表有但没有演示数据。落地：`scripts/seed.py` 造 3 家企业、10 个站点、30 台设备 + 心跳 + 监测数据。

### 13.6 实测踩坑记录（★ 这节是面试最值钱的部分，全是「不亲自跑绝对不知道」的点）

**坑 1：thinking 模式下 `tool_choice="required"` 直接 400。**
现象：`qwen3.8-flash` 默认开思考，传 `tool_choice=required` 返回
`The tool_choice parameter does not support being set to required or object in thinking mode`。
实测四种组合：thinking+required ❌ / thinking+auto ✅ / 关思考+required ✅ / 关思考+不传 ✅。
解法：请求里带 `enable_thinking: false`（LangChain 用 `extra_body={"enable_thinking": ...}` 透传）。
顺带收益：关思考后首字延迟明显下降，Agent 场景本来也不需要长推理。

**坑 2：chromadb 的 Rust 引擎在 Windows 上直接崩进程。**
现象：`scripts/ingest.py` 跑完没有任何报错、退出码 1、连异常都不打印。
定位：`python -X faulthandler scripts/ingest.py` → `Windows fatal exception: access violation`，
崩在 `chromadb/api/rust.py` 的 `_upsert` / `_delete`（连最基本的 upsert 都崩）。
解法：向量库抽象成 `add_chunks / search / get_all_chunks` 三个函数，
本地用 numpy 实现（几十万字够用），生产切 Milvus，业务代码零改动。
**这条能直接回答「你为什么用 Milvus」「换向量库成本多大」。**

**坑 3：`DashScopeEmbeddings` 需要额外装 dashscope SDK。**
报错 `No module named 'dashscope'`。解法：直接用 `OpenAIEmbeddings` 走兼容模式
`/compatible-mode/v1/embeddings`，少一个依赖、少一层版本坑。
配套必须设 `check_embedding_ctx_length=False`：否则 LangChain 会先用 tiktoken（OpenAI 的分词器）
预估 token 再切分，对中文/其他厂商模型会误切甚至报错。

**坑 4：Windows 控制台 GBK 编码，print 中文/✅ 直接 UnicodeEncodeError。**
解法：`app/console.py` 里 `sys.stdout.reconfigure(encoding="utf-8")`，脚本入口调一次。

**坑 5：本地向量库必须原子落盘。**
直接覆盖写 `vectors.json`，写到一半中断 = 整个知识库损坏。
解法：先写 `.tmp` 再 `os.replace` 原子替换。

**坑 6：文档改版后的「脏尾巴」。**
同名文档重新入库时，如果新版 chunk 数变少，旧版多出来的 chunk 会继续被检索到。
解法：入库前按 `document_id` 先删旧 chunk，再用固定主键 `{document_id}:{chunk_index}` 覆盖写入
——同一篇文章改几个字重新导入，是**覆盖**而不是新增，这条也是简历里最容易被追问的细节。

### 13.9 三项工程决策（写下来避免以后反复纠结）

1. **时区**：全项目统一用 `app/timeutil.py`（默认 Asia/Shanghai）。
   踩过的坑：seed 写 UTC、查询按本地时间，导致「现场有数据、平台查不到」。
2. **欠费不兜底**：云端返回 `Arrearage` 时只给中文提示（去充值），
   曾实现本地哈希向量降级但已回退——降级写入的向量与云端向量空间不兼容，混用会污染知识库。
3. **文档位置**：技术方案与审查记录都放在项目内（`docs/`），
   改代码前先看 `docs/技术方案.md` 的模块设计，改完把结论追加到 `docs/代码审查记录.md`。
